# Account recovery must replace every login authority (2026-09-28)

## Finding and user impact

`commit_recovery` already claims the recovery code and transaction, inserts a replacement Passkey, revokes prior Passkeys, Identity sessions, OAuth authorization codes and refresh families, and issues new codes/session in one D1 batch. It did **not** remove the `password_credentials` row or revoke `identity_bindings`. The existing password authentication query joins `password_credentials` without a recovery generation check, so a user or attacker knowing the old password could sign in again after an apparently successful recovery. Provider bindings have an `authentication_enabled` flag and are counted as alternative sign-in authority in account policy, but a deployed federated-login lookup through those bindings was not established in this review; the binding risk is a latent contract violation, not a proven current provider-login bypass.

This contradicts [ADR-0001](../adr/0001-atomic-account-recovery.md)'s atomic switch of account authority and [ADR-0003](../adr/0003-account-platform-redesign.md)'s normalized credential model. The [NIST SP 800-63B-4 invalidation guidance](https://pages.nist.gov/800-63-4/sp800-63b.html) treats invalidation as removing an authenticator's binding to the subscriber and calls for prompt invalidation of compromised authenticators. Research on [risk-based account recovery](https://arxiv.org/abs/2403.11798) underscores that recovery itself is an attack surface; adding risk signals may be worthwhile later, but does not substitute for revoking known old authority.

## Decision and invariants

The existing D1 batch now deletes the principal's password verifier, because `password_credentials` has no lifecycle/revocation column and the row has no referencing foreign keys. The new recovery session may explicitly enroll a new password later. The batch sets every unrevoked provider binding's `authentication_enabled=0` and `revoked_at=now` instead of deleting it, preserving transaction and audit foreign keys. It continues to preserve only the freshly inserted Passkey and freshly issued session. Another principal's credentials remain unchanged.

The revocations are after the recovery-code use claim and successful new-authenticator FK gate, and before the new session insertion, all in the same batch. [Cloudflare D1 batch](https://developers.cloudflare.com/d1/worker-api/d1-database/) executes prepared statements as a transaction and rolls back on failure; [D1 foreign keys](https://developers.cloudflare.com/d1/sql-api/foreign-keys/) are enforced, so deleting bindings would be both historically destructive and potentially invalid. An `UPDATE` affecting zero rows does not fail a batch: the existing unique consumption inserts and authenticator FK still provide the decisive one-use/active-principal gates.

## Concurrency boundary

Recovery revocation alone does not prevent a stale in-flight password authentication from reading and verifying the old hash before recovery, then inserting a session after recovery. Nor does it prevent an in-flight password mutation from re-adding a verifier after recovery if its write is unconditional. Concurrent work in `password.rs` now conditions session issuance on the exact current verifier/hash version inside its D1 batch, with a dependent FK insert forcing rollback on zero rows. Concurrent work in `account_repository.rs` now gates password mutation on a still-live initiating session inside its batch, also forcing rollback on zero rows. A pre-recovery provider-binding callback is likewise gated on the live initiating Passkey session in `binding_repository.rs`; recovery revokes that session. These cross-path guards are part of the same end-to-end invariant, not optional future hardening.

## Verification

- `node scripts/tests/recovery-authority.mjs` uses Node's SQLite with `PRAGMA foreign_keys=ON` and actual migrations `0001`–`0006`; it extracts the two recovery SQL constants from production source. It verifies that the existing password-login join no longer finds the old verifier and that a future provider-login predicate no longer finds an active binding; it also checks referenced history, new/old key state, old session revocation, other-principal isolation, rollback after a one-time recovery-code claim failure, and `PRAGMA foreign_key_check` returning no violations. The provider predicate is a model check, **not** a claim that a production provider-login handler already exists.
- `cargo test -p identity-worker --lib`: 85 passed after concurrent password work was integrated. `cargo clippy -p identity-worker --all-targets -- -D warnings`: passed. The first strict Clippy run during that concurrent edit had found temporarily unused `PasswordChange*` declarations; those warnings were resolved before this final run.
- The SQLite test is a focused SQL/schema regression, not a full WebAuthn browser recovery or deployed Cloudflare D1 test. In particular it does not establish provider-login behavior, which needs an end-to-end test when that path ships.

## Design trade-off

Deleting the password row discards its old version counter, so a newly enrolled password starts at the normal initial version. Existing tokens/sessions are independently revoked in the same batch, so the version is not relied on for revocation. Retaining a cryptographically obsolete hash solely for history would create an active credential under the current schema and would require a migration plus login query changes. The simpler delete is the safer immediate representation.
