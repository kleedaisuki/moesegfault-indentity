# Independent project audit: security and contract findings (2026-09-28)

## Scope and method

This is a targeted source-level review of the Rust Identity Worker, OAuth/OIDC persistence and contracts, account credential transitions, migration constraints, and existing architecture/security notes. It is **not** a deployed-environment penetration test or an exhaustive proof about every route. The email-verification incident and frontend integration are being investigated separately; this note avoids duplicating their ownership. Findings below are prioritized by executable impact, not by style.

## Working-tree resolution status

The findings below describe the **baseline defects**. Subsequent work in this shared working tree addresses all five; this matrix is a status pointer, **not** a claim of deployed remediation. Password-agent final local verification was still pending when the matrix was added.

## P1 — A passwordless account can add a password without the required recent step-up

**Evidence.** [`account.rs` `put_password`, lines 1478–1527](../../crates/identity-worker/src/account.rs) authenticates a live cookie-bound session and validates CSRF via `mutation_session`, but only verifies `current_password` inside `if let Some(existing)`. When `password_credentials` has no row, execution goes directly to hashing and `INSERT`. There is no test of `authenticated_at`, `auth_method`, or an elevated session. The already available [`recent_enrollment_session` predicate, lines 2433–2441](../../crates/identity-worker/src/account.rs) shows how recent password/passkey sessions are checked elsewhere. The public [`PUT /v1/me/password` contract, OpenAPI line 1182](../../openapi/identity.yaml) explicitly says passwordless users must have a recent step-up session.

**Trigger / impact.** With a valid but old or low-assurance Identity session on an account lacking a password (for example a federated-login session), a caller meeting the existing origin/CSRF boundary can establish a permanent new password. The missing authorization gate violates the advertised security contract and can convert a temporarily compromised session into persistent access. This does **not** imply a cross-site attacker can bypass Origin or CSRF; those guards are present.

**Correction.** In the `existing.is_none()` branch require a recent qualifying step-up before the credential insert, returning the established `reauthentication_required` problem when absent. Define precisely which passwordless methods can step up (a recent passkey session is the current obvious case); do not accidentally make legitimate federation-only accounts permanently unable to add a password. Add handler/DB tests for no-password stale/federated session rejection, recent stepped-up session acceptance, and current-password replacement behavior. Keep the HTTP problem and idempotency behavior compatible.

**Confidence:** high (direct branch and explicit OpenAPI contract). No runtime request was executed.

## P1 — Password rotation leaves already-issued sessions and refresh tokens active

**Evidence.** The same [`put_password` handler, lines 1498–1527](../../crates/identity-worker/src/account.rs) reads `password_credentials` and writes only that table. It does not touch `identity_sessions`, `oauth_authorization_codes`, or `oauth_refresh_token_families`; `password_version` is not read by session or refresh-token validation (repository-wide search found it only in credential write/read paths). [`ADR-0003`, line 177](../adr/0003-account-platform-redesign.md) requires recovery and password change to rotate/revoke affected sessions and refresh families in the same logical operation. The recovery transition in [`ADR-0001`](../adr/0001-atomic-account-recovery.md) is explicitly atomic across those authorities.

**Trigger / impact.** A user changes a known-compromised password, but any stolen existing Identity session or OAuth refresh token remains usable through its ordinary expiration and can continue refreshing. Password change therefore does not serve as credential-compromise containment, contrary to the accepted architecture. The effect is not a cryptographic bypass; it is missing revocation semantics.

**Correction.** Decide the intended observable policy (revoke other sessions and refresh families while preserving/rotating the initiating session, or revoke all and require login). Apply the password write and revocations as a single D1 transaction/batch, with an authority gate so concurrent updates cannot silently overwrite one another. If revoking the current session, return the appropriate cookie clearing and frontend navigation; otherwise rotate it and return its new CSRF token. Add tests showing old cookies/refresh generations fail immediately and the current browser follows the documented transition. Because this changes observable login state, stage and document the migration rather than attaching a blind `UPDATE` to the current query.

**Confidence:** high for missing revocation; policy choice is unresolved and requires product/security decision.

## P1 — Pairwise OAuth subject is defeated by global internal identifiers in issued JWTs

**Evidence.** [`oauth.rs::sign_tokens`, lines 925–960](../../crates/identity-worker/src/oauth.rs) puts globally stable `principal_id` in the access-token `pid` claim, and the raw Identity session ID (`sid`) in both access and ID tokens. Every OAuth client receives and can decode its own signed JWT. [`userinfo`, lines 500–553](../../crates/identity-worker/src/oauth.rs) depends on `pid` for profile lookup, while [`logout`, lines 605–659](../../crates/identity-worker/src/oauth.rs) depends on raw `sid`. [`ADR-0002`](../adr/0002-contract-and-d1-boundaries.md) promises pairwise subjects and no `principal_id` disclosure. The advertised discovery metadata says `subject_types_supported: [pairwise]`.

**Trigger / impact.** Two separately registered clients compare `pid` (or `sid` for tokens from the same Identity session) and correlate an end user despite different `sub` values. This is a direct privacy-contract failure, not a theoretical collision. The intended purpose of pairwise identifiers is to prevent such cross-client correlation; see [OpenID Connect Core §8.1](https://openid.net/specs/openid-connect-core-1_0-18.html) and [RFC 9068 §6](https://www.rfc-editor.org/rfc/rfc9068.html) on access-token privacy. The current deployment's public JWK configuration does not make JWT payloads secret: signed JWTs are only encoded, not encrypted.

**Correction.** Do not put global principal/session identifiers in external tokens. Resolve UserInfo from client-scoped `sub` and token audience through the authoritative `pairwise_subjects` relation, or a non-public mapping; check issuer, audience, token use and expiry before lookup. ID-token logout needs an equivalent client-scoped `sid` mapping or another validated mechanism. Handle existing tokens during a short compatibility window (configured access TTL is at most five minutes) and test that two sectors' tokens share no stable global claims while UserInfo and RP-initiated logout still work.

**Confidence:** high. A separate implementation owner was assigned while this review was underway.

## P1 — Password login has no verifiable online-guessing throttle

**Evidence.** [`password.rs::authenticate`, lines 276–360](../../crates/identity-worker/src/password.rs) looks up the account, runs Argon2id (including a dummy hash for missing users), and returns the same authentication failure for bad guesses. It neither reads nor increments a per-account failure budget and does not invoke a rate-limit binding. The password credential table has no failure counter, and a repository-wide search of non-vendor Worker code and Wrangler/infra configuration found no password-login rate-limit rule. [`ADR-0003`, line 110](../adr/0003-account-platform-redesign.md) explicitly calls for guessing limits. [NIST SP 800-63B §3.2.2](https://pages.nist.gov/800-63-4/sp800-63b.html) requires a verifier-side mechanism effectively limiting failed attempts; [OWASP's Authentication Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html) describes login throttling as a basic online-guessing defense.

**Trigger / impact.** A non-browser client can first obtain an anonymous browser context and then send scripted requests with the expected Origin/CSRF headers; browser-origin checks are not a bot rate limit. Attempts against a known login identifier are bounded only by Worker/D1 infrastructure capacity and the password entropy. Every attempt performs a memory-hard Argon2 verification (configured to about 19 MiB), so this is also an availability and cost-amplification path. A separate out-of-repository Cloudflare dashboard WAF rule may exist, but this review cannot verify one; even an IP-only rule would not establish the documented per-account invariant under distributed attempts.

**Correction.** Add an authoritative, bounded per-account/per-authenticator attempt budget with a measured cooldown/recovery policy that does not create permanent denial of service. Put a cheap edge rate limiter/WAF in front to absorb high-volume anonymous traffic, but do not make eventually consistent edge counters the only account-level authority. Keep unknown-user responses indistinguishable, avoid exposing account existence through 429 behavior, and test distributed identifiers, successes/reset, expiry, and concurrent attempts. Provision and monitor the operational rule in version-controlled deployment artifacts.

**Confidence:** high that the repository lacks a throttle; medium about deployed exposure because external Cloudflare dashboard configuration was unavailable.

## P1 — Account recovery leaves the old password credential usable

**Evidence.** [`repository.rs::commit_recovery`, lines 478–529](../../crates/identity-worker/src/repository.rs) atomically creates the replacement Passkey, revokes old Passkeys, sessions, OAuth codes/refresh families, and recovery-code sets, but never removes or disables `password_credentials`. [`password.rs::authenticate`, around line 306](../../crates/identity-worker/src/password.rs) still joins that table and can create a fresh password session for any active principal. Recovery leaves the principal `active`, so a prior password remains an independent live authenticator after recovery. The old [ADR-0001](../adr/0001-atomic-account-recovery.md) described revoking all old authenticators when Passkeys were the only modeled authenticator; the account redesign split password credentials into a separate table without extending this recovery transition.

**Trigger / impact.** A user with both a password and recovery codes completes recovery after password compromise. The old password still authenticates immediately; revoking pre-existing sessions and refresh tokens cannot contain an attacker who knows it. This defeats the expected security purpose of replacing account authority. `identity_bindings` also remains enabled after recovery, but current code does not yet appear to implement federated sign-in from those rows, so that portion is a future-integration exposure rather than a demonstrated current bypass.

**Correction.** Include `DELETE FROM password_credentials WHERE principal_id=?` (or a credential-versioned disable) in the same D1 recovery batch, after the one-time recovery claim and before committing the new session. Decide and document whether active provider bindings should also be disabled/revoked so future federated login cannot silently re-open the recovered account. Test a full password+Passkey+recovery-code account: old password must fail after recovery, new Passkey must succeed, and concurrent recovery attempts remain one-shot. The user-facing recovery result should explicitly explain that the password was removed and can be re-established through the stepped-up account flow.

**Confidence:** high for the old-password path; medium for the as-yet-unimplemented provider-login implication.

## Resolved in working tree — cross-client rotated-refresh replay

The initial review found that `exchange_refresh` called `revoke_family_for_reuse` before comparing `grant.client_id` with the authenticated client. A client presenting another client's **already rotated** refresh token could therefore revoke the rightful client's family. The token is high-entropy, so obtaining it already requires a leak or cooperation; this was a conditional cross-client blast-radius concern, not an unauthenticated guessing path.

The current [`oauth.rs::exchange_refresh`, around line 862](../../crates/identity-worker/src/oauth.rs) calls `classify_refresh_use` before any reuse side effect. `ForeignClient` returns ordinary `invalid_grant` without family revocation; the same-client rotated case still revokes the family. The focused `foreign_client_cannot_trigger_rotated_refresh_reuse_revocation` unit test passed according to the implementation owner. This source inspection confirms the branch order, **not** a D1 end-to-end replay test or a deployed rollout. [RFC 6749 §6](https://www.rfc-editor.org/rfc/rfc6749.html#section-6) requires refresh-token/client binding, while [RFC 9700 §4.14](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14) describes rotation-based replay detection.

## Verification and limits

- Source checks inspected `oauth.rs`, `oauth_repository.rs`, `account.rs`, relevant migrations, OpenAPI, and architecture notes. There was no local D1 integration run, browser test, staging call, or claim that other routes are defect-free.
- Existing code already uses D1 batch/constraint authority gates in OAuth and recovery paths; fixes should reuse those mechanisms rather than a non-atomic read-then-write sequence. See [Cloudflare D1 batch documentation](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch) and [RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html) for refresh-token rotation context.
- The OAuth privacy and password-step-up findings are contract violations independent of research fashion. Emerging ephemeral subject work, such as the [OpenID Connect Ephemeral Subject Identifier draft](https://openid.github.io/connect-ephemeral-sub/main.html), could strengthen unlinkability further but is **not** required to correct the present pairwise-claim leak and is not production-ready merely because a draft exists.
