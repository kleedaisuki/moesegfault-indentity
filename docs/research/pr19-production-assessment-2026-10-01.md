## Authentication and continuation are separate failure boundaries

`apps/login/src/i18n.ts` supplies the shared `loginFailed` heading. `renderLogin` in `pages.ts` catches `authenticateWithPassword` failure and displays the heading plus `ApiError.message`, which uses the problem detail/title. `password::authentication_failed` emits `401`, `authentication_failed`, and `Authentication failed` before a successful authentication response.

The password route intentionally combines unknown or unverified login identifier, missing password authority, inactive principal, password mismatch, and concurrent credential replacement into the same anti-enumeration response. It accepts usernames or **verified** email/mobile identifiers; a registration email/contact alone does not grant login authority. Environment mismatch is a possible boundary to check, not a diagnosis of this user's account. An invalid/expired authorization transaction instead emits `400 invalid_request / Invalid authorization transaction`.

The resume bug occurs **after** successful authentication: production password response constructs a root-relative `/v1/oauth/.../resume`, but Login resolves it against its own `location.href`. Login and Identity have different origins, so the browser remains on Login and the OAuth transaction does not finish. PR #19 replaces that divergent representation with the same absolute fixed-issuer helper already used by Passkey and existing-session paths. The source-level bug remains in production revision `a50482b`.

These are distinct observations. Do not claim the PR resolves a `401` password rejection, ask for passwords, or expose request/response bodies to distinguish them. The useful next evidence is only environment, failed operation path stripped of handles/query, HTTP status, stable problem code, and correlation ID.
