# Code governance evidence for behavior-preserving consolidation

Date: 2026-09-24. Scope: guidance for consolidation of utilities, domain-model refinement, validation-boundary cleanup, and CI in this Rust/TypeScript identity platform. This note is not a security sign-off or a claim that any particular refactor has been validated.

## Local decision context (observed)

- `docs/adr/0002-contract-and-d1-boundaries.md` makes `openapi/identity.yaml` the public HTTP contract and explicitly preserves protocol-specific OAuth/OIDC error and redirect behavior. Accordingly, internal consolidation cannot flatten externally distinct responses.
- `docs/configuration.md` already requires a shared, scope-aware Origin helper for the two browser origins while retaining a narrower WebAuthn origin. This is a concrete example of consolidating mechanism without widening policy.
- `.github/workflows/ci.yml` already uses SHA-pinned actions, minimal top-level `contents: read`, locked dependency installation, Rust format/lint/tests/deny checks, frontend matrix checks, contract and migration tests, artifact packaging, and staging verification. Improving governance should first remove actual gaps or duplication, not create a parallel test framework.
- `docs/adr/0003-account-platform-redesign.md` says the direct-CORS Account SPA is a bootstrap and the BFF is a target architecture. Do not mistake a future architectural aim for a currently enforced trust boundary.

## External evidence and its limits

| Source and status | Observation / source claim | Applicability and limit |
| --- | --- | --- |
| [Fowler, *Refactoring* (2018)](https://www.martinfowler.com/books/refactoring.html), practitioner methodology | Refactoring is a sequence of small, behavior-preserving transformations, reducing error risk and avoiding a prolonged broken state. | A useful workflow, not empirical proof that any abstraction is beneficial. Preserve observable HTTP, UI, migration, and deployment behavior and test at each coherent step. |
| [OWASP Input Validation Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Input_Validation_Cheat_Sheet.html), production security guidance | Validate untrusted input early; distinguish syntactic from semantic validity. Validation does not replace context-specific XSS/SQL-injection controls. | Removing identical checks *within one established trusted flow* can be sound, but the server-side entry boundary and domain invariants must remain. Browser checks alone never establish trust. |
| [OWASP Secure Cloud Architecture Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Secure_Cloud_Architecture_Cheat_Sheet.html), production security guidance | A risk-informed architecture may verify at trust transitions and avoid repeating authentication within a trusted component path; blanket zero-trust checking has performance and maintenance costs. | This is not permission to assume all internal data are trustworthy. Trace origins of data, component boundaries, and persistence re-entry before deleting checks. |
| [GitHub, Protecting against security threats](https://docs.github.com/en/code-security/tutorials/secure-your-organization/protect-against-threats), official operations guidance | Explicit least-privilege workflow permissions and full commit-SHA action pins limit CI supply-chain blast radius. | Already substantially present locally. Review any *new* job/action for permission and pinning rather than adding ceremonial controls. |
| [Rana et al., *Journal of Systems and Software* 157, 110394 (2019)](https://doi.org/10.1016/j.jss.2019.110394), systematic mapping of 142 empirical studies | Reported quality effects of object-oriented refactoring were inconsistent; industrial and academic findings conflicted. | Metrics and code-smell counts alone do not establish benefit. Evidence is mainly OO/Java and predates recent Rust/TypeScript practice. |
| [Rahman, Bird & Devanbu, MSR 2010](https://www.microsoft.com/en-us/research/publication/clones-what-is-that-smell-2/), peer-reviewed empirical study | Most bugs were not significantly associated with clones, and cloned code could be less defect-prone. | Counters a blanket “all duplication is a bug” rule, not proof duplication is harmless in security policy or protocol contracts. Prefer merging synchronized domain rules, not superficially similar but intentionally independent code. |
| [Code reuse and defects, *Empirical Software Engineering* (2023)](https://link.springer.com/article/10.1007/s10664-023-10408-6), empirical study of 12 Java projects / 44,900+ commits | Reuse mechanisms showed nuanced associations: reusability may help, but misuse of inheritance/delegation can worsen outcomes. The authors caution that code churn proxies effort and Defects4J omits some defects. | Supports narrow, explicit composition over hierarchy-for-its-own-sake. Observational Java correlations do not predict causal benefit for this repository. |

## Decision implications (inferred / recommended)

1. Consolidate utilities when callers share *semantics and change cadence*, not merely syntax. Preserve separate wrappers where error mapping, logging, or authorization scopes differ. This is an inference from the contract and clone evidence, not an observed defect.
2. Make parsing/normalization and authorization ownership explicit at the HTTP adapter; represent durable domain constraints in constructors/types or transaction boundaries. Remove repeat checks only after tracing a path showing no new trust transition or independent invariant.
3. For each refactor, name the unchanged behaviors before editing: OpenAPI surface, OAuth exceptions, registration/login/account UI, migration compatibility, and deployment packaging. Run focused tests plus the existing CI gates; add regression tests for discovered gaps rather than duplicate assertions everywhere.
4. Consider a pattern only if it removes a real variation point or invalid state. Prefer small modules and explicit policy objects to deep inheritance or generic dispatch that obscures security decisions.
5. A material revision of this guidance would require local evidence that a removed check protected a distinct attack path, or comparative before/after measurements showing a new abstraction reduced or increased change cost, defects, latency, or CI flakiness.
