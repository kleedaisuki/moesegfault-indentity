# Behavior-preserving architecture refactor opportunities

Date: 2026-09-24. Reviewed branch: `codex/refactor-governance-20260924` at `f85eb22`. Scope: two remaining, bounded Worker refactor slices after the current governance commits. This is a source-level design assessment, not implementation or runtime validation. `openapi/identity.yaml` and the deployed UI/HTTP behavior remain the external contracts.

## Current model and decision constraint

`account.rs` is the HTTP adapter, but still directly implements some account persistence transitions; `account_repository.rs` already owns most identifier and authenticator commands. `api.rs` and `account.rs` each adapt WebAuthn registration options to the same public JSON shape. These are worthwhile boundaries because a future policy change otherwise must modify multiple production paths. They are **not** a reason to create a generic repository framework or to unify protocol-specific OAuth errors with account problems.

| 1 | Move the contact-edit persistence transition from `account.rs::update_contact` (approximately lines 592–698) into a narrow command in `account_repository.rs`, next to `create_contact`/`delete_contact`. The handler should retain HTTP parsing, error mapping, email/mobile normalization and wire formatting; the repository should own the existing three-statement D1 batch and account-scoped readback. **Integration order:** slice 1 first; slice 2 after any concurrent `account.rs` edits land. Each should be a separate commit and CI milestone. The command extraction must leave the HTTP adapter's response branch order intact; an apparently cleaner response mapping can be a public behavior break.

## Deliberate non-targets and risk boundary

- `account.rs::put_password`/`delete_password` also contain direct SQL. Their current read-then-write and "last authentication method" checks interact with database constraints, concurrent enroll/revoke, and credential versioning. Moving or strengthening them without explicit transactional behavior tests is not a low-risk consolidation. Treat as a later design/validation slice, not incidental cleanup.
- `account.rs::revoke_authorization` has a pre-read followed by a D1 batch of grant/family/code revocations. Extracting it is plausible, but changing its conditionality during a behavior-preserving pass could alter concurrent and idempotent semantics. Its adapter size is smaller than the contact transition, so defer until a dedicated grant-lifecycle test exists.
- Similar-looking `authenticated_session`, `secret`, and response helpers in `api.rs`, `account.rs`, `bindings.rs`, and `oauth.rs` intentionally return different projections or protocol errors. Do not merge by syntax alone. In particular, ADR-0002 preserves OAuth/OIDC error formats, redirects, and browser authorization semantics separately from RFC 9457 account errors.

## Evidence and limits

- Local contracts: [ADR-0002](../adr/0002-contract-and-d1-boundaries.md), [ADR-0004](../adr/0004-email-verification.md), [code-governance evidence](code-governance-evidence.md), and the source targets above. Existing CI is `.github/workflows/ci.yml`; this note proposes additions to its existing gates rather than another framework.
- Production platform: [Cloudflare D1 Worker bindings](https://developers.cloudflare.com/d1/worker-api/), including `batch()` and session behavior, make the persistence transition a meaningful single unit. Moving SQL between Rust modules does not itself improve atomicity; preserving the batch and testing transitions is the claimed benefit.
- Research signal: [Rahman, Bird, and Devanbu, MSR 2010](https://www.microsoft.com/en-us/research/publication/clones-what-is-that-smell-2/) and [Rana et al., *Journal of Systems and Software* 2019](https://doi.org/10.1016/j.jss.2019.110394) caution that clone removal/refactoring is not uniformly associated with fewer defects. These are non-causal, mostly non-Rust results; they justify semantic selection and regression evidence, not an expected defect reduction estimate. [A 2025 EASE longitudinal study](https://doi.org/10.1145/3756681.3756948) likewise reinforces that repeated refactoring is no substitute for measuring defect outcomes, but it does not identify the right abstraction for this project.

This recommendation would be revised if a domain/integration test shows one WebAuthn caller intentionally uses a different option policy, or if the contact edit's current SQL is already being replaced by a separately accepted contact lifecycle design. No performance benefit is claimed. The probable benefit is lower policy drift and clearer state ownership, conditional on behavior tests staying green.
