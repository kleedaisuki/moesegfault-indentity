# Security-boundary governance assessment (2026-09-24)

## Scope and decision

Question: which request checks are duplicated or lack a distinct threat model, without changing public HTTP behavior, UI, or weakening CSRF/authentication protections? This is a source review, not a penetration test. The paired Login/Account origins, cookie-bound CSRF tokens, transaction binding, endpoint-specific authentication, idempotency, and bounded body reads are treated as required contracts. Working tree inspection only; no runtime probe was performed.

## Tests to make a consolidation safe

1. Route-matrix test: every state-changing route must state `Caller`/origin scope, whether idempotency-wrapped, body media type/limit, and CSRF source. Include Login and Account origins, foreign/missing Origin, and direct Account routes.
2. Preclaim ordering: invalid origin, CSRF, content type and oversized body must create no idempotency row or domain side effect; replay should not bypass caller proof.
3. Compatibility golden cases: missing/invalid Idempotency-Key; missing cookie; wrong/expired CSRF; malformed Content-Type; bodyless methods; `Content-Length` absent, false-small and oversized; exact problem status/title and CORS headers.
4. Browser journey: Login anonymous ceremony, Account session writes, avatar upload/delete, password deletion, and authorization revocation. In particular cover Account-origin mutations to prevent recurrence of the 2026-09-19 outage.

## External evidence and limits

- [OWASP CSRF Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html): custom request headers, tokens, Origin verification, Fetch Metadata, and its compatibility/rollout caveats.
- [MDN Fetch Metadata](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Fetch_metadata): `Sec-*` headers are browser-forbidden to script, but server policy must account for request context and caches.
- [Cloudflare Workers Request API](https://developers.cloudflare.com/workers/runtime-apis/request/): Content-Length is not inherent to every body representation; do not treat its presence as a size guarantee.

Inference: an exact-origin + session/transaction-bound CSRF combination should withstand browser CSRF without strict Fetch Metadata checks. This does **not** address compromised first-party JavaScript/XSS, leaked CSRF tokens, malicious browser extensions, or non-browser clients; Fetch Metadata does not solve those either. The recommendation would change if abuse telemetry showed a distinct attack blocked only by Fetch Metadata or if clients demonstrably depend on its current strict rejection behavior.

## 2026-09-24 implementation follow-up: Fetch Metadata fallback

The Worker mutation entry points in `guard.rs`, `idempotency.rs`, `account.rs`, and `bindings.rs` now reject an explicit `Sec-Fetch-Site: cross-site` signal rather than requiring exactly `same-site` and `Sec-Fetch-Mode: cors`. Exact configured `Origin`, the existing browser/session-bound CSRF checks, content-type checks, and direct-route guards remain in place. This intentionally **expands acceptance** for requests with absent or alternate Fetch Metadata; it does not relax the rejection of a browser-reported cross-site request. The change does not touch CORS response policy, cookie attributes, or the public success response. The previous strict policy and the new fallback are not wire-identical for legacy clients, so this is a compatibility/security-policy decision rather than a purely mechanical refactor.

Evidence and limits: [OWASP's CSRF Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html) recommends rejecting an explicit cross-site signal for unsafe methods and using Origin verification as a fallback when Fetch Metadata is missing; [MDN's `Sec-Fetch-Site` reference](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Sec-Fetch-Site) describes the browser-generated signal and its values. The repository's pure guard tests cover absent, same-site, same-origin, `none`, unknown, and cross-site values, and separately check the origin/CSRF primitives; Worker unit tests, Clippy, and formatting passed locally. These tests do **not** prove end-to-end request ordering or measure the deployed client population. No production telemetry of rejected legacy requests was available at decision time. A staged rollout should monitor 403 rates by coarse request context and revert or narrow the fallback if a distinct blocked abuse path appears. Do not log raw cookies, CSRF tokens, or personal identifiers.
